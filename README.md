# F.A.C. V2 USB CDC bootloader

Bootloader for the **F.A.C. V2** (Floppy Ant Controller, STM32F072CBT6). It lets the FacTool update the firmware over
USB **without drivers**: the board stays a CDC serial port. An interrupted update leaves the board in the bootloader,
ready to repeat the installation. The bootloader **does not update itself**: it is installed only with ST's ROM DFU
(BOOT button), the FacTool's DFU recovery or STM32CubeProgrammer.

The full specification (memory map, structures, protocol, startup) is `docs/firmware-specs/bootloader.md` in the
FacTool; the changes required in the application firmware are in `firmware-bootloader.md`, next to it.

## At a glance

| Area | Addresses | Contents |
|---|---|---|
| Flash, pages 0–7 | `0x08000000`–`0x08003FFF` | bootloader; info block `"FACB"` at `0x080000C0` |
| Flash, pages 8–62 | `0x08004000`–`0x0801F7FF` | application; header `"FACA"` at `0x080040C0` |
| Flash, page 63 | `0x0801F800` | "application valid" record `"FACR"` |
| RAM | `0x20000000`–`0x200000FF` | application vectors copied to SRAM + shared block `"FACS"` at `0x200000C0` |

- **At every reset** the bootloader checks the application (header, vectors, record, CRC-32) at 8 MHz, before any
  initialisation, and starts it. It stays active if the application is missing or invalid, if the application asks
  for it (command `8` from the FacTool) or if the application restarted 3 times without confirming the boot.
- **Debug** builds of the application (flag in the header) start without a record and without boot counting, for
  debugging with an ST-LINK.
- **In bootloader mode:** USB CDC with the same VID/PID as the application (`0483:5740`), product
  `FAC_V2 Bootloader`; motor and servo outputs driven low; LED with two short blinks per second (it blinks at every
  packet while writing). If it was entered on request and receives no commands for 60 s, it goes back to the
  application.
- **Protocol v1** with `A5 cmd seq len payload crc32` packets: `INFO`, `ERASE`, `WRITE`, `VERIFY`, `BOOT`.

## Layout

| Path | Contents |
|---|---|
| `FAC_V2_Bootloader.ioc` | STM32CubeMX configuration (**CMake** toolchain) |
| `Core/`, `USB_DEVICE/`, `startup_stm32f072xb.s` | CubeMX generated code; our code only in the `USER CODE` sections |
| `Core/Src/Bootloader/`, `Core/Inc/Bootloader/` | bootloader logic (ours) |
| `Core/Inc/Bootloader/fac_boot_shared.h` | shared addresses and structures: **copy it unchanged into the firmware** |
| `fac_bootloader.ld` | linker script (16 KB flash, RAM from `0x20000100`, info block at `+0xC0`) |
| `Drivers/`, `Middlewares/` | ST's HAL/LL, CMSIS and USB Device Library |
| `tests/` | host tests of the logic, with simulated flash and peripherals |
| `docker/`, `scripts/` | build environment and scripts |

The logic accesses the hardware only through `fac_bl_port.h`: on the board it is implemented by
`fac_bl_port_stm32.c`, in the tests by a simulator. This way protocol, checks and startup are tested without the
board.

## Build, flash and debug in VS Code

1. Install the **STM32Cube for Visual Studio Code** extension (recommended by `.vscode/extensions.json`).
2. Open the folder and accept the CMake configuration offered by the extension (`Debug` or `Release` preset).
3. "FAC V2 Bootloader: build, flash and debug (ST-LINK)" builds, flashes and stops at `main`.

The Debug configuration is built with `-Os -g3` (like Release, with symbols): with `-Og` the bootloader would exceed
16 KB.

## Build and test in Docker

Only Docker is needed. The script builds the image (Arm GNU Toolchain 13.3, CMake, Ninja) on first use.

```sh
sh scripts/fac-bl.sh build Release   # or: build Debug
sh scripts/fac-bl.sh test            # host tests of the logic (UBSan on; ASan with -DFAC_TESTS_ASAN=ON)
sh scripts/fac-bl.sh clean
```

On Windows there is also `scripts\fac-bl.ps1` with the same commands. The output is in `build/<preset>/`:
`FAC_V2_Bootloader.elf`, `.hex`, `.bin`. The build prints the memory usage: the bootloader must fit in 16 KB.

## Size

The 16 KB limit is enforced by the linker script (the build fails if it is exceeded). Measures taken:

- RCC and GPIO with the **LL** drivers instead of the HAL (set in the `.ioc`, Project Manager → Advanced Settings);
- flash erased and written through registers in `fac_bl_port_stm32.c`;
- `USE_USB_DOUBLE_BUFFER=0` in `CMakeLists.txt`: the CDC class does not use double-buffered endpoints.

## Regenerating the code with CubeMX

The code is generated by STM32CubeMX 6.15 (FW_F0 V1.11.5) from `FAC_V2_Bootloader.ioc`. After every
"Generate Code":

- check that the `FAC_BL_*` calls are still in the `USER CODE` sections of `main.c` and `usbd_cdc_if.c`;
- the build uses `fac_bootloader.ld`; `STM32F072xx_FLASH.ld`, recreated by CubeMX, is not used (and is ignored by git);
- the CRS (HSI48 synchronised to the USB SOF) is enabled by `FAC_BL_early_init()`, not by the `.ioc`;
- rebuild and check the memory usage (it must stay below 16 KB).

## Version

`FAC_BL_VERSION_*` in `Core/Inc/Bootloader/fac_bl_config.h`, encoded like the firmware version
(`major·10000 + minor·100 + patch`). It ends up in the info block and in the `INFO` reply.
